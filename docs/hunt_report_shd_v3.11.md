## КРИТИЧЕСКОЕ 1. Воронoi-решётка видит только начало потока

`partial_fit()` буферизует строки до `target_buf = min(max_init_buffer, max(4500, 12·M))`
и **один раз** строит решётку. Дальше новые строки лишь подвигают центры уже
существующих ячеек. Редкий режим, пришедший **после** окна прогрева, в кристалл
не попадает.

| доля потока, где живёт режим | строк режима в кристалле (ожидалось ~15) |
| :--- | :---: |
| 0 % | 102 |
| 2 % | 106 |
| 5 % | 83 |
| 7.5 % | 17 |
| **10 %** | **0** |
| 25 % | 0 |
| 50 % | 0 |
| 75 % | 0 |
| 90 % | 0 |

`N=60 000, M=300` → окно решётки 4500 строк = 7.5 % потока.
Зонд: `_hunt/check_lattice_window2.py`.

**Почему это плохо для продукта.** Поздний режим — это ровно тот случай, для
которого существует `heal_domain_shift` и «bounded forgetting». Но:

* радар **тоже** ловит поздний режим (BW 0.772 против 0.185 на норме);
* и лечится он нормально, если подставить окно с метками: 18 строк режима
  в кристалле после heal (зонд `_hunt/check_heal_late.py`).

То есть **радар работает, а перегонка — нет**: дистиллятор кристалла не
покрывает второй половины потока, и «лечение» дергается за то, что дистиллятор
не видел. Плюс `heal` без меток кладёт в `crystal_Y` **оценки новизны** вперемешку
с настоящими целями — это отдельная находка (см. ниже).

**Смягчающее обстоятельство.** На PM2.5 (единственный time-ordered датасет) окно
решётки — 4500 строк при 4750 обучающих, то есть 94.7 % обучающего окна, и
95.8 % критических строк лежат внутри. Поэтому опубликованные числа PM2.5
этим дефектом **не ломаются** (зонд `_hunt/check_pm25_position.py`).

**Что делать.** Пересобирать решётку по мере накопления (периодически, с
переносом ячеек), либо честно объявить в README, что кристалл покрывает только
первые `max(4500, 12·M)` строк, а всё остальное — только через `heal`.

## КРИТИЧЕСКОЕ 2. Сдвиг внутри обучающего потока отравляет радар: 100 % ложных тревог

Паспорт — это **второй момент** эмбеддинга `E[u uᵀ]`, а не ковариация. Сдвиг
среднего в потоке смещает и паспорт, и новое окно, поэтому BW-расстояние между
ними схлопывается. Сдвиг, присутствующий в обучающих данных, «съедает» радар.

Контролируемый эксперимент: поток 40 000 строк, последние X % — сдвинутый режим
(+3σ по всем фичам, +12 по y). Считаем BW на **нормальных** окнах (очевидно
in-distribution):

| доля сдвига в потоке | ложных тревог на нормальных окнах | BW | порог |
| :---: | :---: | :---: | :---: |
| 0 % | 0/40 (0 %) | 0.0775 | 0.1202 |
| 1 % | 0/40 (0 %) | 0.0708 | 0.1202 |
| 2 % | 0/40 (0 %) | 0.0863 | 0.1202 |
| **5 %** | **40/40 (100 %)** | 0.1343 | 0.1202 |
| 10 % | 40/40 (100 %) | 0.1844 | 0.1202 |
| 20 % | 40/40 (100 %) | 0.2810 | 0.1202 |
| 30 % | 40/40 (100 %) | 0.3677 | 0.1202 |

Зонд: `_hunt/check_fa_scan.py`.

**5 % сдвига в обучающих данных → радар кричит на абсолютно нормальных данных.**
Для системы раннего предупреждения это инверсия: ложная тревога дороже
пропущенной аварии в любой разумной модели цены.

Причина — ровно та, что описана выше: решётка построена по первым 4500 строкам
(чистый фон), а паспорт (второй момент по всему потоку) вобрал сдвиг.

## КРИТИЧЕСКОЕ 3. Порог радара зашит под rank=32, а `rank_passport` — публичный параметр

`save_hologram(rank_passport=...)` — публичный API, но порог `0.085` откалиброван
для rank 32. Смена ранга молча ломает калибровку:

| `rank_passport` | BW на in-distribution | порог | флаг |
| :---: | :---: | :---: | :--- |
| 16 | 0.0390 | 0.1202 | — |
| 32 (штатно) | 0.0638 | 0.1202 | — |
| 64 | 0.1023 | 0.1202 | — |
| **128** | **0.1606** | 0.1202 | **SHIFTED** |
| **256** | **0.1811** | 0.1202 | **SHIFTED** |

`rank_passport=0` → `eigvals[-0:]` = все 256 собственных значений (не 0!).
`rank_passport=-1` → 255. Никакой валидации нет. Зонд: `_hunt/check_rank_edges.py`.

То же с порогом в статье: paper говорит «feature covariance», а в коде — второй
момент. Для Bures–Wasserstein между матрицами это одно и то же название для
разных объектов; в тексте расходится с реализацией.

## СЕРЬЁЗНОЕ 4. Метрика BW — это второй момент, а не ковариация: она слепа к форме распределения

Проверено напрямую. Метрика инвариантна к повороту распределения **только если**
совпадает и среднее; сдвиг среднего она ловит сильнее, чем изменение формы.

| тип возмущения | BW | флаг |
| :--- | :---: | :--- |
| in-distribution | 0.0632 | — |
| **сдвиг уровня** c=+0.25 (среднее, форма сохранена) | **0.1282** | **SHIFTED** |
| сдвиг уровня c=+0.50 | 0.2250 | SHIFTED |
| поворот t=0.25 (среднее сохранено) | 0.0821 | — |
| поворот t=0.50 | 0.1471 | SHIFTED |
| **тяжёлый хвост** (10 % строк × 6, среднее сохранено) | **0.0727** | **—** |

Зонд: `_hunt/hunt_semantics.py`.

Тяжёлый хвост — 10 % строк, умноженных на 6, — радар не видит вообще. Для
промышленной телеметрии (забитый датчик, удар, накопление) это опасный класс
отказов. Зато «насос стал на 4 % теплее» — тот самый дрейф, ради которого
строился радар, — даёт 0.128 при пороге 0.120: **ложная тревога на ровном
медленном дрейфе**.

Гипотеза о «слепых направлениях» (сдвиг в отброшенных 32 из 256 собственных
направлений) **не подтвердилась**: специально построенный сдвиг, возбуждающий
только отброшенное подпространство, оказался виден наравне с обычным
(0.446 против 0.376). Это хорошая новость для метода — и она означает, что
проблема не в ранге паспорта, а в его смысле.

## СЕРЬЁЗНОЕ 5. `heal` без меток смешивает в `crystal_Y` две разные величины

`heal_domain_shift(X, y=None)` пишет в `crystal_Y` **оценки новизны**
(`‖u‖² − ‖P u‖²`), а не цели. В одном кристалле оказываются два несовместимых
масштаба:

```
исходные цели (реальные):   84.86 .. 112.98
инъецированные (новизна):     0.66 ..   0.91
```

`get_training_data()` возвращает их одной конкатенацией. README обещает
«`get_training_data()` → train any model on 1.7 % of data». Для безъярного
потока (а это и есть промышленный сценарий: `shd_watch learn` работает без
меток) это неверно.

Проверено через CLI, ровно как в документации:

```
$ shd distill --input stream_nolabel.csv --output clf.npz   # unsupervised_mode: true
$ shd heal --crystal clf.npz --input drift_nolabel.csv --output hlf.npz
   -> crystal_Y: первые 5 = [2.927 2.862 2.853 ...]  (спектральный леверидж)
                  последние 5 = [0.591 0.788 0.716 ...] (оценки новизны)
```

Зонд: `_hunt/hunt3.py` (раздел D).

## СЕРЬЁЗНОЕ 6. K-Means-базовая линия отдаёт меньше точек, чем заявлено

`bench_seeds.py:107`:
```python
idx = np.argmin(cdist(km.cluster_centers_, Z_tr, metric="sqeuclidean"), axis=1)
```
`argmin` берёт **по одной** ближайшей строке на центр. Если два центра выбирают
одну и ту же строку — она попадает в корсет дважды.

На синтетике 81D, 17 010 строк, M=300:

| | запрошено | возвращено | **уникальных** | дубликатов |
| :--- | :---: | :---: | :---: | :---: |
| K-Means (базовая линия) | 300 | 300 | **265** | 35 |
| SHD | 300 | 300 | **300** | 0 |

То есть «equal budget M=300» — на самом деле 300 против 265 у K-Means.
SHD получает преимущество, которого не зарабатывал. SHD-часть здесь чистая
(все медоиды — разные строки потока, это проверено отдельно).

Зонды: `_hunt/check_kmeans_dup.py`, `_hunt/check_shd_distinct.py`,
`_hunt/km_dup_fast.py`.

## СРЕДНЕЕ 10. Паспорт и `n_seen` расходятся после лечения

`heal_domain_shift` увеличивает `n_seen` на число инъецированных строк и
одновременно **блендит** паспорт с новым окном. После лечения паспорт — не
второй момент полного потока, а смесь, а `n_seen` утверждает, что поток вырос.
`summary()` отдаёт `compression_ratio = n_seen / len(X)`, то есть после лечения
эта величина бессмысленна: 8000 → 8400 при 335 медоидах.

Зонд: `_hunt/hunt4.py` (раздел C).

## СРЕДНЕЕ 11. «Anytime mode» отдаёт нерепрезентативный префикс

`finalize_crystal()` сортирует медоиды по занятости ячейки **по убыванию**.
`get_training_data(budget_points=k)` возвращает первые k — то есть самый
плотный фоновый край кристалла:

| бюджет | критических строк | доля |
| :---: | :---: | :---: |
| 25 | 2 | 8.0 % |
| 50 | 2 | 4.0 % |
| 100 | 5 | 5.0 % |
| 150 | 15 | 10.0 % |
| 300 (весь кристалл) | 34 | 11.3 % |

Средний вес гаммы первых 25 — 2.068, последних 25 — 0.274. То есть префикс —
это ровно тот конец кристалла, где редкого режима меньше всего. Для «anytime»
режима, который заявлен в docstring загрузчика, нужен либо иной порядок
(например, стратифицированный), либо честная оговорка.

Зонд: `_hunt/hunt_anytime.py`.

## МЕЛОЧИ

* **CLI не умеет в собственный shipped-артефакт.** `artifacts/superconduct_v37.npz`
  не содержит проектора, и `shd radar` / `shd heal` на нём падают с `ValueError`.
  README это знает, но артефакт лежит в репозитории и в `spectral_hologram_v37_release.zip`

* **CLI не экспонирует половину API.** `critical_threshold`, `auto_band_ratio`,
  `passport_recalibrate`, `new_weight_boost`, `protect_old_weight_frac`,
  `use_residual`, `weighting="uniform"` — в `shd/cli.py` нет ни одного.
  README §6 рекомендует пресеты, до которых нельзя дойти из командной строки.
* **Абсолютные пути Windows** в `bench_metro_watch.py:62`,
  `bench_scania_cost.py:69`, `_verify_metro.py:19`.
* **`data/pm25.csv` — обрезанная копия.** В репозитории 6 392 строки (5 937
  пригодных), в опубликованном артефакте — 41 757. `bench_pm25.py` качает из
  сети, так что воспроизвести опубликованные числа PM2.5 офлайн нельзя.
  Локальная копия годится только для структурных проверок.
* **Радар при B=1 практически бесполезен:** порог 0.68, а BW на нормальной
  строке 0.837 → сдвиг. Порог расширяется как `0.085·√(1024/B)`, и при B=1
  это 0.85.
* **40 % спектральной массы выбрасывается.** Для 81D: top-32 держат 59 %
  следа, 41 % отброшено. Это ожидаемо (данные rank ≤ 81, паспорт 32), но
  стоит быть в README явно, а не в подвале.
* **Радар не «видит» содержимое кристалла.** Окно из собственных медоидов
  кристалла даёт BW 0.256 против 0.188 для сырых строк. Радар оценивает
  паспорт, а не ячейки.

## ЧТО ОКАЗАЛОСЬ НЕ ДЕФЕКТОМ

Честный раздел: часть гипотез я проверял и они **не подтвердились**.

* **float16-паспорт.** Первый зонд показал 63 % расхождение BW — это был мой
  собственный баг (использовал rank 256 вместо 32). Изолированный прогон
  (`_hunt/isolate_p1.py`) даёт: отклонение BW из-за float16 — **3e-6…4e-5
  абсолютно** (относительно 1e-4…1e-3). Порог 0.085 от этого не страдает.
* **Слепые направления.** Гипотеза «сдвиг в отброшенных направлениях не
  виден» — **не подтвердилась** (см. критическое 4).
* **Жёсткий кап лечения.** `max_crystal_size` держится на всех значениях
  1…200, при недостаточном капе бросается `ValueError` **до** мутации
  загрузчика, и загрузчик остаётся нетронутым. Отличный контракт.
* **Медоиды — настоящие строки.** 100 % медоидов SHD — дословные строки потока
  (проверено на 12 произвольных и на всех 300 в полном кристалле).
* **Детерминизм.** Один и тот же сид → побайтово идентичный кристалл.
* **Режимы не смешиваются.** Переключение supervised/label-free посреди потока
  отвергается.
* **Веса нормированы.** Среднее гаммы = 1.0000.
* **Round-trip.** `loader.save()` → `load` воспроизводит кристалл точно.
* **Устойчивость к краям.** Одна строка, константные фичи, выброс 1e6 —
  все обрабатываются, кристалл строится.
* **Статистика в артефактах честная.** Мой шим `wilcoxon` (точный
  перестановочный) даёт p-значения, **совпадающие** с артефактами до
  последней значащей цифры. Медианы README совпали с JSON до знака.
* **Тесты репозитория проходят** — 112/112.
* **PM2.5-результаты этим дефектом не ломаются** (см. критическое 1).

## ПРИОРИТЕТ

**Сначала 1 и 2 — они бьют по главному заявлению продукта.** SHD заявлен как
«нулевой GPU, стриминговая дистилляция с ранним предупреждением о сдвиге
домена». Находка 2 показывает, что при 5 % сдвига в обучающих данных радар
объявляет тревогу на нормальных данных — 100 % ложных срабатываний. Находка 1
показывает, что вторая половина потока в кристалл не попадает. Обе — следствие
одной конструктивной ошибки: **решётка и паспорт строятся по разным
подмножествам данных** (решётка — по началу потока, паспорт — по всему).

Минимальное исправление, которое стоит сделать: пересобирать решётку (или
хотя бы пересчитывать паспорт) по всей выборке, а не по окну прогрева, и
калибровать порог на in-distribution данных, а не константой из чужого
датасета.

Затем 6 (бейзлайн) и 9 (статья без раздела о стоимости отказа) — они
стоят дешевле и бьют по доверию к цифрам.
