# Разбор проекта Spectral Hologram Distiller (SHD v3.11.0)

Дата разбора: 2026-10-21. Объём: ядро `shd/` (1350 строк), 39 бенчмарк-скриптов,
52 JSON-артефакта, 4 файла тестов (108 test-функций), README (47 КБ), paper/main.tex,
два аудита, стратегический план, «письмо инженеру», история Colab-ноутбука.

---

## 1. Что это вообще

Потоковая дистилляция датасета в файл-«кристалл»: 300 реальных медоидов вместо
17 000 строк (1.76 %), CPU-only, без GPU, без облака, плюс встроенный детектор
сдвига домена (Bures–Wasserstein по спектральному «паспорту»), плюс хирургическое
самоисцеление при дрейфе.

Пять шагов пайплайна (по коду, не по README):

1. **RFF-скетч Бухнера**, двухмасштабный: `Ω_low ~ N(0, 0.75/√d)`, `Ω_high ~ N(0, 2.10/√d)`,
   k = 256 гармоник, `U = √(2/k)·cos(ZΩ + φ)` со строчной нормировкой. Онлайн-аккумуляторы
   `Ψ = UᵀU`, `Φ = Uᵀy` → память O(k² + d), а не O(n). Прогрев буферизован жёстким
   капом 8192 строк, поэтому `cdist` на этапе решётки никогда не даёт O(N²)-всплеск.
2. **Триггер «фазового пика»**: ridge-предиктор `W = (Ψ̂ + βI)⁻¹Φ̂`, счёт
   `residual_ratio + 2·y_z²`, порог — 84-й перцентиль. Три хвоста: `high/low/both`.
   В безъярном режиме (`y=None`) новизна синтезируется спектральным левериджем
   `s_i = u_iᵀ(Ψ̂ + βI)⁻¹u_i` — Cholesky, без меток вообще.
3. **Фазовое многообразие** `[Z ‖ κ·y_norm]`, κ = 3.2. Одна непрекрывающаяся
   Воронoi-тесселяция, k-means++ seeding, 4 итерации Ллойда, затем **snap к реальным
   точкам** (медоиды, не синтетические центроиды). 26 % ячеек зарезервированы под пик.
4. **Взвешивание**: kernel herding через FISTA (250 шагов) поверх вокселевого приора
   `p^0.55`, финальный бленд `w = 0.75·p̂^0.55 + 0.25·γ*`.
5. **Паспорт**: top-32 собственных пар Ψ̂ во float16 + BW-радар с порогом
   `0.085·max(1, √(1024/B))`, плюс `heal_domain_shift` (инъекция 35 медоидов,
   бленд паспорта `α = clip(B/(n_seen+B), 0.15, 0.50)`, жёсткий кап `max_crystal_size`)
   и `DomainBank` (кристалл на домен + маршрутизация по ближайшему паспорту).

CLI (`python -m shd`): `inspect / distill / radar / heal`. Загрузчик: `get_training_data()`,
`get_phase_peak_slice()`, `check_domain_shift()`, `heal_domain_shift()`.

## 3. Самое сильное в проекте

Это не «достижение нейросети», а честная инженерная работа. Главный актив — не
алгоритм (он опубликован и воспроизводим), а **дисциплина доказательств**:

- `METHODOLOGICAL_AUDIT.md` сам у себя нашёл 10 дыр и **отозвал 6 заявлений**:
  «zero catastrophic forgetting», «sub-ms радар», польза двухмасштабного RFF,
  residual-триггер как механизм редкого режима, «kernel herding несущий»,
  «гарантирует редкие ячейки». Это редкая вещь: авторский аудит, который убивает
  собственные формулировки.
- `AUDIT_v311.md` (рус.) закрывает стратегические дыры измерением: forgetting
  (0.265 → 0.549, ×2.07 за 9 сдвигов), метрика (официальная стоимость Scania
  500·FN + 10·FP), стоимость на железе (артефакт 29–185 КБ, но процесс 58–69 МБ).
- `ARTIFACTS.md` — манифест: каждый JSON разнесён на canonical / supporting / working,
  с указанием скрипта-генератора и «вопроса, на который он отвечает». Никаких глоссов.
- Отрицательный результат (MetroPT-3, 0/4 утечек у паспорта против 4/4 у z-score)
  не спрятан, а **вынесен в лид-письмо инженеру** как аргумент доверия.
- Код написан в стиле «контракт, а не предположение»: жёсткий кап лечения бросает
  `ValueError` **до** мутации загрузчика; неоднозначный NPZ без ключа `X`
  отвергается с объяснением, а не угадывается; `reshape(-1)` вместо `squeeze()`
  везде, где одномерный массив схлопывается в скаляр.

В коде нет ни одного `except:`, ни одного `TODO`. По `shd/` нет ни одного
абсолютного пути (они только в бенчмарк-скриптах — см. ниже).

## 4. Риски (собранные из всех источников)

### 4.1 Единственный самый сильный результат не имеет артефакта

README §6: при `high_band_ratio=0.65` и M=600 кристалл **бьёт oracle** на
критических метриках (KRR 15.51 против 17.59, GBM 12.08 против 12.72). Рядом
стоит честная приписка: свип был разовым рабочим скриптом, per-seed JSON не
закоммичен, «перезапустите с `--save-json` перед тем, как цитировать».

Это единственное место, где автор честно признаёт, что цифра в тексте не
воспроизводима. Проблема в том, что именно эта цифра — самая продаваемая
(«корест обыгрывает полный датасет на критическом режиме при 3.5 % данных»).
Дилемма: либо коммитить артефакт, либо снимать строку. Сейчас висит третье
состояние — цифра есть, воспроизводимости нет.

### 4.2 Paper отстаёт от аудита

`paper/main.tex` до сих пор:

- в аннотации — «≈ 98 KB, 70× compression», тогда как замеры дают 28.9 КБ (4D) /
  184.9 КБ (синтетический 81D); 98 КБ — историческая сериализация, что сам аудит
  признаёт неактуальным;
- не содержит PM2.5-отрицания в аннотации — а это второй реальный датасет;
- не раскрывает null-результаты двух абляций (двухмасштабный RFF, residual-триггер),
  которые аудит требует раскрыть;
- не описывает CPD-rank (заимствованный код вендорился в `vendor/`, но метод в
  тексте отсутствует — «текстовый долг»);
- §4.5 описывает только одноразовое исцеление A→B, а не исправленный
  трёхсдвиговый lifelong-бенчмарк.

То есть репозиторий честнее своей статьи. Это странная, но не плохая позиция:
как артефакт — лучше, как публикация — отстаёт.

### 4.3 Рабочее дерево не в git

HEAD репозитория — коммит `v3.10.0`. Версии в `pyproject.toml`, `shd/__init__.py`
и тестах — **3.11.0**, README озаглавлен «v3.11.0 working tree». При этом
`git status` показывает ~25 неотслеживаемых файлов, включая `ARTIFACTS.md`,
`PITCH.md`, `EMAIL_ENGINEER.md`, `bench_metro_watch_v2_results.json`,
`bench_latency_v2_results.json`, `bench_scania_cost_official_results.json`,
`bench_edge_envelope_v2_results.json`, `bench_bank_scaling.py`, `bench_edge_envelope.py`,
`bench_latency.py`, `bench_metro_watch.py`.

То есть **значительная часть «проверенного и исправленного» состояния существует
только на диске**. Риск потери — реальный; риск потери истории правок — тоже
(коммита на v3.11 нет, откатиться не на что). Плюс `bench_seeds.py` в рабочем дереве
изменён, а опубликованные oracle-числа считались на старой версии.

Мелочь, которая мешает аудиту: рабочее дерево переписано в **CRLF**, коммит — в LF.
Из-за этого `git diff --stat` показывает 36 220 изменённых строк вместо реальных
919 (`git diff --ignore-cr-at-eol`). Любой, кто посмотрит на diff, увидит шум.

### 4.4 Абсолютные пути Windows в бенчмарках

`bench_metro_watch.py:62`, `bench_scania_cost.py:69`, `_verify_metro.py:19` жёстко
зашиты на `C:\Users\User\Downloads\New folder\...`. Воспроизводимость вне машины
автора — **ноль**. Для проекта, чья главная ценность — проверяемость, это
недопустимо: путь должен приходить из аргумента или переменной окружения.

### 4.5 Половина API недоступна из CLI

В конструкторе и в `heal_domain_shift` есть `critical_threshold`, `auto_band_ratio`,
`passport_recalibrate`, `new_weight_boost`, `protect_old_weight_frac`, `use_residual`,
`herding_mix`, `voronoi_temper`, `weighting="uniform"` — но CLI их не экспонирует
(в `shd/cli.py` нет ни одного из этих имён). README рекламирует `critical_threshold`
и `passport_recalibrate`, а из командной строки их не вызвать. Для «продуктового»
слоя это разрыв между заявленным и доступным.

### 4.6 Заголовочное сжатие противоречит рекомендациям

Шапка README обещает «0.3 %–1.8 % от строк». §6 рекомендует M = 600 — это
**3.5 % (SC) / 3.75 % (reactor)**, то есть вне заявленного диапазона. Аудит предлагал
переписать на «0.2 %–3.8 %» или ввести адаптивное `M = clip(N/28, 300, 1200)`.
Сейчас в тексте живут оба утверждения.

### 4.7 Дефолты заведомо неоптимальны, и это признано

Собственная абляция репозитория: `high_band_ratio=0.50` даёт 2.737 K против 3.440 K
у дефолта, `tail_quantile=94` — 2.735 K. Это **−21 %** на критической метрике.
Дефолты оставлены, потому что на них построены опубликованные таблицы. Это
легитимно, но в README это надо написать громче, чем «дефолты консервативны»:
пользователь, который возьмёт дефолты, получит результат на 21 % хуже доступного.
Аудит это уже записал.

### 4.8 Порог BW откалиброван на одном датасете

`0.085` подобран на superconductivity heal-бенчмарке. Для нового домена придётся
перепроверять in-distribution false-alarm rate. Признано в Known limitations, но в
продукте нужен **квантильный режим калибровки** (порог = квантиль расстояний на
здоровом периоде), а не константа из чужого датасета. `shd_watch.py` это уже
делает для тревоги-бюджета; сам радар — нет.

### 4.9 Нет ни одного своего датасета

Всё — публичное: UCI superconductivity, PM2.5, Scania APS, MetroPT-3, синтетический
реактор. Стратегический план (`PLAN_STRATEGY_KZ.md`) прямо фиксирует дыру №2 как
открытую и не решаемую кодом. Для пилота это единственный по-настоящему
блокирующий риск: письмо инженеру (EMAIL_ENGINEER.md) уже отправлено — теперь
ждём ответа, а не пишем код.

### 4.10 Мелочи, которые я бы починил

- `bench_seeds.py` при падении OpenML молча уходит на California Housing — это
  правильно (заголовок меняется), но артефакт должен хранить, **какой** датасет
  реально использовался, иначе «UCI Superconductivity» из JSON нельзя отличить от
  фолбэка постфактум.
- `bench_*.py` пишут результаты относительно CWD — нет `--output` у всех подряд
  (в `bench_deltas.py`/`bench_passport.py` уже добавлено, в остальных — нет).
- `load_superconduct()` тянет OpenML по сети. Для офлайн-воспроизведения нужен
  локальный кэш, как уже сделано для Metro (`metro_cache.py`) и Scania.
- Тесты покрывают M ≤ 200 и `br ≤ 0.30`. Путь M = 600 / br = 0.65 — рекомендованный
  §6 — не покрыт ни одним тестом. Аудит это уже отмечал; в текущем дереве есть
  `test_crystal_size_scaling_and_wide_band`, но он синтетический.

### P2 — качество метода

11. **C-порт ядра под Cortex-M** (RFF + паспорт + BW). Python+NumPy — это 58–69 МБ;
    на микроконтроллере без переписывания не поедет, и это признано в README.
    Зато именно это и есть «продуктовый слой, который нельзя скопировать за выходные».

## 6. Итог

Ядро сделано грамотно: bounded memory, честные контракты вместо предположений,
ноль `TODO`/`except:`, самодостаточный артефакт с проектором. Цифры README
перепроверяются по артефактам с точностью до знака — редкая и ценная вещь.
Методологическая дисциплина (аудит, отзывающий собственные формулировки,
манифест артефактов, вынесенный в лид отрицательный результат) выше среднего
на порядок.

Но проект сейчас в состоянии «сильный черновик релизной версии». Три вещи мешают
ему стать цельным: рабочее дерево не в git; сильнейшая цифра (§6, корест бьёт
oracle) не подкреплена артефактом; статья отстаёт от честности репозитория.
Всё три — технические, не научные, и все три закрываются за день-два работы
плюс один длинный прогон бенчмарков.

Число, вокруг которого всё и держится: **корест из 300 точек на 1.76 % данных
 обыгрывает Kernel Thinning и Supervised Kernel Thinning на критическом режиме
 20/20 сидов (p = 1.9e-6)** — при честно отрицательном глобальном качестве
 на PM2.5 и честно отрицательном результате на Metro. Второе важнее первого.
